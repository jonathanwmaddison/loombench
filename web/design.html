System design

How a match is executed: which component owns what, every call made to the model in a round, and the data exchanged at each interface.

Engine identifiers keep the weaving vocabulary of the code. They map to the terms of the report as follows: weaver = agent; ground, in warps = share of the loom, in width units (100 in total); passage = round; yarn = design; press = claim share; yield = concede share; carry = maintain position; offer = propose joint ownership.

1. Division of responsibility

Code owns the state

The loom, the legal actions, the limits and the outcome of every interaction are computed by code. Options are enumerated from the current state and written out as sentences that carry the relevant quantities.

The model weighs options

Jev (POST /v1/systemone) receives a state, an instruction and a list of options, and returns a probability for each option. It never produces text and never sees a coordinate.

Code samples and records

An action is sampled from the returned distribution with a seeded generator. Every response is stored, so a match can be re-executed exactly without calling the model.

3. Lifecycle of a match

Figures are from match 3 of run main (5 agents, 26 rounds): 185 calls, $0.0108, 11.9 s. Calls within a phase are issued concurrently.

Set-up code

Assign personas and objectives (deal); build each agent's prompt prefix (castOf); seat the agents in a seeded order; give each 20% of the loom and its starting design.

Group decision: border 10 calls

Each agent states a preference (5). The other four rate the proposer's choice (4). If any refuses, the proposer keeps it, defers, or takes the least-objected option (1).

26 rounds 165 calls

Phase 1: 130 action calls (5 per round). Phase 2: 24 response calls. Phase 3: 11 reply calls. Six rows of the rug are woven after each round.

Group decision: title 10 calls

Same procedure, over titles composed by code from what happened in the match.

Scoring code

scoresOf reads each agent's final share and design history; recordOf keeps the assignment, the results and the tape.

4. One round: three phases

Each phase is one batch of concurrent calls, at most one call per agent. Phases 2 and 3 are issued only to the agents an interaction concerns; a round in which no claim is contested makes 5 calls.

Phase 1 · Action
5 calls, one per agent (id p<round>.<agent>). Four questions in each:
  • move (choice): maintain, claim from the left or right neighbour, concede to either, propose joint ownership.
  • yarn (choice): keep the design, start a new one, reduce it to one colour, or adopt a neighbour's pattern, colour or whole design. Omitted while a newly adopted design is held for its first 2 rounds (24 of 130 calls here).
  • bold (score, 4 anchors): the magnitude of a claim or concession.
  • fine (score, 4 anchors): the scale of the pattern.
↓
Code samples each answer, applies design changes, and compares what the two agents on each shared edge intend. Uncontested moves (a concession; a claim met by a concession) are applied at once. A claim on a neighbour who did not concede, two claims on one edge, and a proposal of joint ownership each open an interaction.
Phase 2 · Response
0–5 calls, one per agent with something to answer (id ….a), one question per interaction:
  • To a claim: accept, refuse, or counter-propose joint ownership of the contested units.
  • To a proposal of joint ownership: accept or decline.
  • To a simultaneous claim (both agents asked): hold, give way, compromise, or propose joint ownership.
The question states what was actually done: by whom, how many units, each party's current share.
↓
Code closes every interaction that was accepted or declined, and identifies the claimants who were refused or received a counter-proposal.
Phase 3 · Reply
0–5 calls, one per such claimant (id ….r):
  • After a refusal: override it, withdraw, or compromise on half.
  • After a counter-proposal: accept it, override, or withdraw.
↓
Code settles each interaction (how far the edge moves and how it is joined: interlocked, straight, two-colour, open slit, or a knot where a claim was withdrawn), weaves six rows, and records each agent's share.

Limits enforced by code: no agent is offered a claim once it holds 46% of the loom; a concession cannot reduce a share below 3 units; an agent whose share reaches zero is offered a place again in the next round.

6. The model interface

Validation. A choice answer is accepted only if it gives a probability for exactly the options sent, the probabilities sum to 1 within rounding, and the stated choice is the maximum. A response that fails, or a call that exceeds 8 s, is not used: the engine draws from a uniform distribution with the seeded generator and marks the decision by: "script". The runner retries a failed call twice. The record counts these as fallbacks.

Prompt construction. instructions = prompt prefix (identity, persona sentence, objective sentence) + facts from the agent's recent history (for example "Last passage: Ashley gave Amanda ground, freely.") + the question. Facts that should affect a decision are placed in the instruction, not the state. Options are shuffled per call, because a model favours the option listed first.

Every stochastic element (seating, the options offered, their order, each draw) has its own named seeded stream. The model's responses are the only non-deterministic input: the same seed queried twice gives different matches, which is why the response tape, not the seed, is what reproduces a match.

8. Peer communication

peerAsker wraps ask, so the engine is unchanged. For each action call that has a neighbour among its options it makes two further calls, adding about 250 calls to a match.

9. Switches

A match is run under one setting of each switch, and its record keeps them (conditions, with the model and the assignment). Each switch is implemented at one point, so the rest of the code path is unchanged. Three wrap or replace ask; two are in what a seat is told; one is an engine setting; one is in what the engine is given at the start.

In every setting each agent starts with the same area, 20 of the loom's 100 width units. The switches combine, except that peer communication needs a model, five deciding agents and areas that can change, and a solo match needs assigned designs. A chat model is a second decision system and not another model behind Jev's interface: the prompt below is a rendering of Jev's request, the reading sees the host's twenty likeliest first tokens, and a preference for a letter stays in the distribution (it is spread over the options by the seeded order they are listed in).

What the solo agent is told. Nothing about the switch. Its prompt prefix, the state and the options are built by the same code as in a group match, and at the first round the request is identical to the group match's. From then on the two differ only through what the other seats did.

Comparing runs. Two runs made from the same match designs that differ in one switch are paired by match design (bench/compare.mjs); the Controls page lists every such pair. A run folder holds one setting, and the runner refuses to add a match made under another.

10. Records, replay and scoring

Replay. replay(record) calls weave with the record's seed, assignment, settings and tape. The engine takes each response from the tape in place of a call, so it rebuilds the same state, the same questions and the same rug. The match page does this in the browser; the test suite asserts that the replayed cloth is identical.
